One HTTP request, nine subsystems. Here is the exact route a portal action takes — from the browser, through identity and authorization, down to the cloud — and how the response comes back. Every arrow is an HTTP request; every dashed arrow is its response.

The cast

Nine moving parts sit between a button press and a provisioned VM. The credential column matters: it is what each hop checks, holds, or hands to the next.

1 · Who can reach whom

The call graph. Solid edges are HTTP; the browser only ever talks to nginx — every downstream service is hidden behind it.

2 · Login: minting the session

The authorization-code flow. The single-use artifacts (state, PKCE code_verifier, the code itself) live only in this exchange — they are consumed once and gone.

The login handshake, in words

  1. GET /api/auth/begin?provider=lldap.The login page starts OIDC by asking identity-service for a Dex authorize URL (handler main.py → auth.begin()). Purpose: hand the browser a URL to redirect to, while making the server the owner of the CSRF/PKCE secrets before Dex is ever contacted.
  2. authorizeUrl (state + PKCE stored server-side).auth_state.py:begin() mints state = secrets.token_urlsafe(32) and code_verifier = secrets.token_urlsafe(48), stores them in _state_store with a 600 s TTL, and returns {"authorizeUrl","state","provider"}. The URL embeds state, code_challenge = base64url(sha256(code_verifier)), and code_challenge_method=S256. The verifier never leaves the server.
  3. GET /dex/auth (redirect: state, code_challenge, connector).The browser follows authorizeUrl to Dex. This is the OIDC authorization request — it carries state + code_challenge + connector_id=lldap but authenticates nothing yet; Dex responds by showing its login form.
  4. LDAP bind (uid + password).The actual credential check, performed by Dex’s LLDAP connector, not identity-service: Dex binds to LLDAP:3890 as its service account, searches ou=people for the typed uid, then re-binds as that user with the submitted password. A failed bind ends the flow at the login form.
  5. user record (uid, mail, cn).LLDAP returns the matched entry. Dex maps uid→sub (a base64 protobuf, not the raw uid), mail→email, cn→name into the id_token claims.
  6. 302 back with code + state.Dex redirects the browser to the portal’s /auth/callback with a single-use authorization code and the echoed state. The code is the only proof-of-login artifact the browser carries.
  7. POST /api/auth/exchange {state, code}.The SPA’s callback page sends {"provider","code","state","redirectUri"} to main.py (exchange). From here the server — not the browser — performs the token swap.
  8. consume state + code_verifier (single-use).auth_state.py:consume_state() pops the stored entry, rejecting missing/reused/expired state with 400 auth_bad_state. This single-use pop is what makes state CSRF-resistant.
  9. POST /dex/token (code + verifier + client_secret).dex.py:exchange_code() POSTs grant_type=authorization_code, code, redirect_uri, client_id=libcloud-portal, client_secret (server-side only), and the recovered code_verifier. PKCE proves the same party that requested the code is redeeming it.
  10. id_token + refresh_token.Dex returns the tokens. The id_token carries the verified identity; the refresh_token is the long-lived secret, and it is deliberately not sent onward to the browser.
  11. verify id_token (iss / aud / exp).dex.py:verify_id_token() fetches Dex’s JWKS and checks signature, iss, aud=libcloud-portal, exp, and sub. A tampered token → 401 auth_invalid_id_token.
  12. resolve internal user + role.users.py:resolve_on_login() maps the verified external identity to an internal principal. For LLDAP logins it recovers the uid and reads the role OpenFGA holds (fga.role_for(uid), → int-<uid>); for federated identities it may instead return a collapse or pending outcome. dex.py:external_identity() builds the <provider>:<sub> subject stored in linkedIdentities.
  13. role + cloud capabilities.OpenFGA answers with the role and per-cloud {cloud, canView, canProvision, canUpdate}, so the SPA renders only the tenants this user may access.
  14. Set-Cookie: libcloud_portal_sid (httpOnly, 8 h).session.py:create() mints an HS256 session JWT (internalUserId, role, email, linkedIdentities, sid, iat, exp, jti, 8 h), sets it as an httpOnly cookie, stores the refresh token server-side in _refresh_store[sid], and returns the session JSON.

3 · An unauthenticated request, in depth

Every session begins with no credential. A browser that arrives without a cookie is turned away with 401, then walked through the full OIDC dance — Dex authenticates against LLDAP, and identity-service mints the session JWT. This is the same exchange §2 summarizes; here it is request by request.

The same exchange, in words

  1. GET /api/session — SPA boot.The React app fires this on load to ask “am I already logged in?”. It is a plain GET to nginx, reverse-proxied on /api/* to identity-service:8766, carrying no Cookie header. If a valid cookie were present this would return 200 + the session JSON; here there is none.
  2. sessions.read finds no cookie.SessionService.read() looks up libcloud_portal_sid in req.cookies; the lookup returns None, so no JWT decode is attempted.
  3. 401 auth_no_session.The route raises APIError("auth_no_session","No session",401); the handler returns HTTP/1.1 401 with body {"error":"auth_no_session","message":"No session","details":{}}. No Set-Cookie and no token are produced.
  4. GET /api/auth/begin?provider=lldap.The SPA route guard redirects to /login; the login page calls this to start OIDC. A GET with only the provider query param (redirect_uri defaults to http://localhost:3000/auth/callback).
  5. Mint state (32 B) + PKCE code_verifier (48 B); store 600 s TTL.AuthService.begin() generates state = secrets.token_urlsafe(32) (≈43 chars) and code_verifier = secrets.token_urlsafe(48) (≈64 chars), derives code_challenge = base64url(sha256(verifier)), and stores {code_verifier, provider, redirect_uri, exp} in _state_store for 600 s. The verifier never leaves the server.
  6. { authorizeUrl, state }.200 with {"authorizeUrl":"http://…/dex/auth?client_id=libcloud-portal&redirect_uri=…&response_type=code&scope=openid+profile+email&state=…&code_challenge=…&code_challenge_method=S256&connector_id=lldap","state":"…","provider":"lldap"}. The browser navigates to authorizeUrl.
  7. GET /dex/auth?connector_id=lldap, code_challenge=S256.The browser follows the redirect to Dex (nginx proxies /dex/* → Dex:5556). The GET carries state, code_challenge, code_challenge_method=S256, scope, and connector_id=lldap — still no credential.
  8. 302 to the LDAP login form.Dex finds no dex_session cookie and redirects to its LDAP login form (/dex/auth/local?req=…&state=…) so the user can type credentials.
  9. POST /dex/auth/lldap/login (uid + password).The user submits the form; the browser POSTs login=<uid>&password=<pw> (form-encoded) back to Dex.
  10. LDAP bind (admin) + search ou=people, then bind as the user.Dex authenticates to LLDAP:3890 with its admin service account, searches ou=people for the typed uid, then re-binds as that user with the submitted password. The password check happens at LLDAP, not at identity-service.
  11. user record (uid, mail, cn).LLDAP returns the matched entry. Dex maps uid→sub, mail→email, cn→name for the id_token claims.
  12. 302 to /auth/callback (code + state).Dex redirects the browser back with ?code=<authorization code>&state=…. The code is the single-use OAuth artifact handed to the next step.
  13. POST /api/auth/exchange {state, code}.The SPA callback page sends JSON {"provider":"lldap","code":"…","state":"…","redirectUri":"http://localhost:3000/auth/callback"} to identity-service.
  14. consume state + code_verifier (single-use).consume_state() pops the entry from _state_store — missing/reused/expired state returns 400 auth_bad_state — recovering the code_verifier and the original provider/redirect_uri bound at /begin.
  15. POST /dex/token (code + verifier + client_secret).identity-service calls Dex server-to-server with application/x-www-form-urlencoded: grant_type=authorization_code, code, redirect_uri, client_id=libcloud-portal, client_secret, and code_verifier (PKCE).
  16. id_token + access_token + refresh_token.Dex validates the code + PKCE pair and returns all three tokens. Only the id_token drives login; the refresh_token stays server-side.
  17. verify id_token (JWKS sig, iss, aud, exp, sub).identity-service fetches Dex’s /dex/keys (JWKS) and verifies the id_token signature plus iss/aud=libcloud-portal/exp/sub, then derives the external identity.
  18. resolve internal user + role.identity-service maps the verified identity to an internal principal (user:<uid>) and reads its role from OpenFGA (a /read of the tenant role tuples).
  19. role + cloud capabilities.OpenFGA returns the role plus per-cloud {cloud, canView, canProvision, canUpdate}, so the SPA renders only the tenants this user may access.
  20. Set-Cookie: libcloud_portal_sid (HS256 JWT, httpOnly, 8 h) + session JSON.identity-service mints an HS256 session JWT with claims {internalUserId, role, email, linkedIdentities, sid, iat, exp, jti} (8 h), sets it as an httpOnly; SameSite=Lax; Path=/; Max-Age=28800 cookie, and returns 200 with the session JSON (internalUserId, role, linkedIdentities, email, clouds). The Dex refresh_token is held in _refresh_store[sid], never sent to the browser.

4 · An authenticated request, end to end

The same path serves read and write. A list (GET /api/resources/nutanix) is shown; a provision adds catalog discovery then a POST /v1/compute/nodes at step 13.

The same request, in words

  1. GET /api/resources/nutanix + Cookie: libcloud_portal_sid.The browser sends the session cookie with a GET for the Nutanix tenant’s resources (a read). A provision would add catalog discovery and a POST /v1/compute/nodes at step 13 of the diagram.
  2. verify session JWT (HS256).identity-service decodes and verifies the cookie with session_secret, checking exp. Invalid or expired → 401 auth_invalid_session.
  3. Check can_read(principal, nutanix).identity-service calls OpenFGA /check with the tuple key user:<principal> can_read nutanix_cluster:<tenant> to decide whether this user may view the Nutanix tenant.
  4. allowed.OpenFGA returns {"allowed":true}; a deny would surface as 403 authz_forbidden and the request would stop here.
  5. provisioner OIDC token (aud: libcloud-rest).identity-service mints a different token for the backend hop — a Dex login as the provisioner service account with audience libcloud-rest. The portal token’s aud=libcloud-portal would not be accepted by libcloud.rest.
  6. bearer JWT.Dex returns the provisioner bearer JWT, valid for the REST API.
  7. GET /v1/compute/nodes + Bearer JWT + X-Provider-Connection.identity-service proxies to libcloud.rest:8765 with Authorization: Bearer <jwt> and an X-Provider-Connection header carrying {provider, config:{region,secure}, auth_binding} — note no cloud credentials travel in this header.
  8. verify JWT (JWKS) + policies.json.libcloud.rest validates the bearer against Dex’s JWKS and checks the GET /v1/compute/nodes route against policies.json scope rules.
  9. Check relation (scope / principal).libcloud.rest re-checks authorization in OpenFGA using the token’s scopes and principal.
  10. allowed.OpenFGA permits the call.
  11. resolve vault_user (tenant parent vault_user).libcloud.rest reads the tuple tenant:<tenant> parent vault_user:<…> to find this tenant’s Vault AppRole identity name.
  12. libcloud-nutanix.OpenFGA returns the tenant’s vault_user id (libcloud-nutanix), which names the Vault AppRole.
  13. read AppRole material (orchestrator token).libcloud.rest uses the department-orchestrator token to read secret/data/libcloud-vault-auth/libcloud-nutanix.
  14. role_id + secret_id.Vault returns the AppRole role_id and secret_id — the login material, never exposed to the browser.
  15. POST /auth/approle/login.libcloud.rest exchanges role_id + secret_id for a short-lived tenant token.
  16. tenant token (60 m TTL).Vault mints a tenant-scoped token carrying the department’s read-only policy.
  17. GET secret/libcloud/nutanix (tenant token).Using the tenant token, libcloud.rest reads the actual cloud credentials.
  18. Prism credentials.Vault returns {key, secret, host} — the Nutanix admin username/password and Prism URL.
  19. POST login (Basic auth).libcloud.rest logs into Nutanix Prism with HTTP Basic auth using those credentials.
  20. Set-Cookie: session.Prism returns a session cookie (cached ≈1 h and replayed for subsequent calls).
  21. GET v4 resources (Cookie).libcloud.rest calls the Prism v4 resources API presenting the session cookie.
  22. resource JSON.Prism returns the raw resources (VMs / clusters).
  23. 200 {nodes, categories}.libcloud.rest shapes the raw cloud data and returns 200 with {nodes, categories}.
  24. 200 JSON (shaped resources).identity-service returns the final shaped resource list to the browser.

5 · Logout: invalidating every credential

Logout clears the browser credential and revokes the refresh token — but it is honest about what a signed JWT can and cannot be revoked. POST /api/logout runs three cleanups and then stops: stock Dex offers no IdP-side logout page to call.

The logout handshake, in words

  1. POST /api/logout + Cookie: libcloud_portal_sid.The browser logs out; main.py (logout) reads the session cookie. Goal: clear every credential that proves this session.
  2. decode cookie to recover sid.session.py:revoke() decodes the JWT to recover the sid — the key into the server-side refresh store.
  3. pop _refresh_store[sid] (refresh_token + id_token).It drops the server-side entry holding the Dex refresh token + id token, so the session can no longer be silently renewed.
  4. Set-Cookie: libcloud_portal_sid (Max-Age=0).delete_cookie tells the browser to discard the cookie. Caveat: the JWT itself is not blocklisted — a stolen copy stays valid until exp (8 h), which the table below makes explicit.
  5. POST /dex/token/revoke + token=refresh_token.dex.py:revoke_token() revokes the refresh token at Dex over RFC 7009. It is best-effort: a failed revoke is logged and never blocks logout.
  6. 200 (refresh token revoked).Dex confirms revocation (or the failure is swallowed — the cookie and server-side store are already cleared by the caller).
  7. { "logged_out": true }.identity-service returns {"logged_out": true}; the SPA clears sessionStorage and navigates to /login. There is no IdP-side redirect because stock Dex v2.41.1 has no RP-initiated logout endpoint (GET /dex/auth/logout 404s).

A note on “single-use”

Only the login artifacts in §2 are genuinely one-time. Everything after login is a bearer value replayed verbatim until it expires — there is no nonce, request signing, or token denylist on the API path.

Single-use

  • OAuth state & PKCE code_verifier — popped once
  • OAuth authorization code — consumed at Dex
  • OIDC nonce — popped once
  • pending-identity jti — denylisted on use

Replayable until expiry

  • Portal session cookie — 8 h, no jti check
  • libcloud.rest bearer JWT — ~15 min–24 h
  • Prism session cookie — cached 1 h
  • Vault orchestrator token — 32 days (reads AppRole auth material only)
  • Vault tenant AppRole token — 60 min, tenant-scoped
