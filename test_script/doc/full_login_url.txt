  This is an OpenID Connect (OIDC) Authorization Request sent to Dex (an OIDC identity provider). Let me break it down piece by piece.

  Full URL parts

  http://localhost:5556/dex/auth
    ?client_id=libcloud-rest
    &redirect_uri=http%3A%2F%2F127.0.0.1%3A8766%2Foauth%2Fcallback
    &response_type=code
    &scope=openid+email+profile
    &state=libcloud-dex

  1. http://localhost:5556/dex/auth

  The authorization endpoint of Dex running locally on port 5556. This is where the user's browser is redirected to start the login flow (Dex shows its
  login / connector-picker page here).

  2. client_id=libcloud-rest

  Identifies which OAuth client is asking for authentication. Dex must have a registered client called libcloud-rest (with a matching redirect_uri and
  secret). This is how Dex knows who is calling and which config to apply.

  3. redirect_uri=http://127.0.0.1:8766/oauth/callback

  (URL-decoded: http://127.0.0.1:8766/oauth/callback)

  The callback URL your app (libcloud-rest) exposes. After the user logs in at Dex, Dex redirects the browser back here with the code and state params. It
  must exactly match one of the redirect URIs registered for libcloud-rest in Dex's static config, otherwise Dex rejects it.

  4. response_type=code

  Asks for the Authorization Code flow — Dex will issue a temporary code (not a token directly). Your backend later exchanges this code (plus the client
  secret) at Dex's /token endpoint for access_token / id_token. This is the most secure/standard OIDC flow for server-side apps.

  5. scope=openid+email+profile

  Requested OIDC scopes (the + is URL-encoded space):
  • openid — required for OIDC; tells Dex to issue an id_token.
  • email — requests email and email_verified claims.
  • profile — requests user profile claims (name, username, etc.).

  6. state=libcloud-dex

  An opaque anti-CSRF value. Your app generates it before redirect, stores it in the user's session, and compares it against the value Dex echoes back in
  the callback. If they don't match → reject (prevents login-CSRF / confused-deputy attacks). (Here it's a static string, which is weak — should ideally be
  random per request.)

  Typical end-to-end flow

  1. Browser → /dex/auth?... (this URL)
  2. User authenticates at Dex (or via upstream connector: LDAP, Google, etc.)
  3. Dex redirects browser → http://127.0.0.1:8766/oauth/callback?code=XXX&state=libcloud-dex
  4. Your backend validates state, then POSTs to http://localhost:5556/dex/token with code + client_secret → gets id_token + access_token
  5. Backend verifies the id_token signature, extracts claims, creates a session/JWT for the user.

  GET http://localhost:8765/v1/compute/nodes is a read endpoint. Per authorization.md:194-209, libcloud REST's policy.py enforces it by checking can_read on
  the backend object aws_region:{auth_binding} (default aws_region:aws), with fallback can_provision. So an "auditor" role must satisfy can_read on
  aws_region:aws without satisfying can_provision.

  Authorization here is layered (authorization.md:222-237), so "configure in OpenFGA" actually requires edits in four places — OpenFGA model + tuples, LLDAP
  identity, libcloud REST JWT scopes, and the principal map. Below is the precise recipe.

  6. libcloud REST — JWT scopes + principal map (REQUIRED, else OpenFGA never runs)

  OpenFGA is Layer 3 in authorization.md:222-237. Layer 2 (libcloud JWT scopes in app/auth/identity.py PRINCIPAL_SCOPES) runs first; if the auditor's JWT
  lacks the compute:read scope, the request is rejected before OpenFGA is consulted. So:

  • In ../libcloud.rest/app/auth/identity.py PRINCIPAL_SCOPES, add aws-auditor (and *-auditor) → ["compute:read"] (mirror the viewer entry). Without this,
    GET /v1/compute/nodes 403s at the scope layer.
  • In ../libcloud.rest/data/principal_map.json, add an alias so the Dex sub=aws-auditor resolves to the OpenFGA principal slug. The current file only has
    the legacy cloud-admin/readonly/denied entries:

  aws-auditor does not match that pattern, so the script will run the GET catalog/node calls (steps 5-6) — exactly what you want. Just leave PROVISION
  unset; the dry-run exit at provision_aws.sh:70-73 will stop before POST /v1/compute/nodes. If someone force-sets PROVISION=1, OpenFGA's can_provision
  check (Step 4 above denies it) returns 403 from libcloud REST — that's the safety net.

  Net effect for GET /v1/compute/nodes

  libcloud REST policy.py runs, for user:aws-auditor:

  1. can_connect on libcloud_api:main → ✅ (auditor is a member of tenant:aws, which is parent of libcloud_api:main)
  2. can_use on provider:aws → ✅ (same member path through tenant:aws → parent → provider:aws)
  3. Read scope → can_read on aws_region:aws → ✅ via tenant_auditor (tupleToUserset walks tenant:aws → tenant → aws_region:aws, then resolves auditor on
     tenant:aws, which user:aws-auditor holds)

  POST /v1/compute/nodes would fail at step 3's can_provision because auditor is not in the can_provision union — the auditor can list nodes but never
  create them.
